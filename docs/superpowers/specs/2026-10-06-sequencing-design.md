## 0. 一句话

机器的输入缓冲从**裸 FIFO** 变成**可重排缓冲**：默认关（逐位不变），打开后在
**已入缓冲的件**里挑优先级最高的先加工；策略侧新增第七个头 **Q**，候选 = 缓冲里的件。

## 2. ⭐ 语义裁定：**(A) 缓冲内优先级**，不是 (B) 等指定件

> 这是本批**唯一需要用户拍板**的事（§55.3(a) 已标）。下面给出分析与建议。
> **建议 = (A)**。请用户确认后动工。

### 2.1 两条语义（写死）

**(A) 缓冲内优先级（priority among buffered jobs）**
机台空闲时，在**此刻已在 `in_q` 里的件**中挑优先级最高的先加工。
机台**只要缓冲非空就永不闲置**（非延迟 / non-delay 性质，与今天一致）。

**(B) 等指定的下一件（wait for a designated next job）**
机台只加工**被指定的那一件**；它没到就**闲置**。
可精确复现一份外部算好的计划，但**允许"有活可干时闲置"**。

### 2.2 三条后果对照

| | **(A) 缓冲内优先级** | **(B) 等指定件** |
|---|---|---|
| **(i) 与已发表方法的可比性** | 二者都在**同一个非延迟解码器**下执行：把 (OS, MS) 染色体解码成"每道工序一个优先级"，机台按同一规则取件。**决策空间、解码器、动力学三者同侧**，是公平对打。复现不了它们的**数字**（它们的仿真器没有运输/故障/换型——§55.3(b) 已定），但这不是新增损失。 | 更接近"执行它们的计划"。但**数字照样复现不了**（同 §55.3(b)：本仓有拥堵/故障/换型/充电/交期）。多出来的保真度**买不到可比性**，反而使两边的**解码语义不同侧**：它们跑"精确执行"，我们跑"在线优先级"。 |
| **(ii) 我们自己的策略** | **赚**。决策空间严格变大一格，且是在**已有的非延迟类**里变大：机台不会因新动作变坏（最坏 = 选回 FIFO 队首）。六个头全保留。 | **亏**。现有"候选打分 + 一次 softmax"的骨架**表达不了**它：被指定的件通常**还不在缓冲里**（在别的机台/在途），候选集无从枚举。若给策略一个"闲置"动作，训练早期的最优就是**乱闲置**（代价被后置），DRL 会先学会摸鱼；还要防"永久闲置"死锁。 |
| **(iii) 实现成本** | **小**（见 §3）：一个 Store 子类 + 一个回调 + 一个快照字段 + 一个头。约 **0.5 人日** DES + **1 人日**策略侧。 | **大**（≥ (A) 的 3–5 倍）：每台机要存"在等谁"、要**在每次投递时唤醒重判**、要有活性/死锁守卫；且这一路径**默认关**时必须完全不碰（回归面大）。另外它**引入一个今天不存在的状态**：机器有活可干时闲置——能耗/利用率/`busy` 语义、`horizon` 护栏都要重新定义（闲置的机器可能在 `horizon` 内跑不完 ⟹ 掐表）。 |
| **建模性质** | 只是"取件顺序"变了；**动力学其余部分不动** | **引入闲置决策**——这是一次**建模变更**，不是加一个头 |
| **与本仓纪律** | 关态可做成**构造层面**的零改动（§3.4） | 关态要对每台机查一个"等待"状态——关态与开态的代码路径**必然分叉** |

### 2.3 建议与理由

**取 (A)。** 三条理由，按权重排：

1. **(A) 不引入新状态，(B) 引入闲置。** 本仓的 `MachineSim` 从建立至今**没有"有活不干"这一态**；
   加上它要动能耗口径、`busy` 语义、`horizon` 护栏与活性论证。用户此前已叫停"继续加机制"；
   排序是**补洞**，不该顺手改模型。
2. **同侧规则（§58.4 待办 2）只在 (A) 下可满足。** 基线（NSGA-II / HGS）产出的是
   **静态优先级表**，我们的 Q 头产出的是**状态依赖优先级**——两者是**同一个决策空间、
   同一个解码器**的两种使用者。这正是"RL 对规则"的标准优势来源，是公平的。
   (B) 下基线与策略分属两种语义，比较重新变成不对等。
3. **成本差一个量级**，而 (B) 多买到的只是"精确复现一份外部计划"——而那份计划的数字
   在本仓动力学下**本来就不等于已发表数字**（§55.3(b)）。为一笔买不到的东西付 3–5 倍成本，
   不划算。

### 2.4 (B) 的处置：**延期，不是否定**

(B) 有它唯一的正当用途：**审稿人要求"精确执行 HGS 的计划"** 时。届时它是**基线侧的解码器**，
不是策略侧的机制（无 Q 头、无策略训练）。**登记为开放线索**（§9 第 4 条），本批不做。
同样登记：**(A′)** "(A) + 有限等待（缓冲空时可等 δ 分钟）"——它是 (B) 的弱化版，同样延期。

### 2.5 ⚠️ (A) 的边界声明（必须写进论文）

- (A) **不是** OS 编码。策略产出的是**缓冲内优先级的在线决策**，不是一条完整工序排列。
  论文只能说"机台队列重排（缓冲内优先级）"，**不得**声称"我们优化 (OS, MS) 两段染色体"。
- (A) 的**表达力上界**：机台**看不见还没到的件**。跨机台的顺序仍只能通过 L 头（派车时序）
  间接影响。"先送谁"仍是提前规划，"到了之后谁先上"才是本机制。
- (A) 下机台**不会**为了等一个更合适的件而闲置 ⟹ 它**不能**降低"机台空转"造成的 makespan 损失；
  它改的是**换型顺序、交期紧迫度、剩余工时**这三类可重排的收益。

## 3. DES 侧入口

### 3.1 对 §55.4 草图的评估

§55.4 的草图（"`_PriorityStore(simpy.Store)` 覆写 `_do_get` 按优先级弹（约 12 行）……
**`des.py:485` 一行不改**（优先级是缓冲对象的属性，不是消费者的）；默认 `dispatch=None` ⟹ 裸
`Store` + `pop(0)` ⟹ 既有读数逐位不变"）。

| 草图的判断 | 评估 |
|---|---|
| 覆写 `_do_get` 是正确切入点 | ✅ **已核 4.1.2 源码**：`Store._do_get` = `if self.items: event.succeed(self.items.pop(0))`；`_trigger_get` / `Get.__init__` 两条路径都会走到它 ⟹ 一处覆写覆盖"机台空闲时已有件"与"机台等着、件刚到"两种情形 |
| `des.py:485` 不用改 | ✅ 对——**只要 item 仍是四元组**。⚠️ 但**"优先级是缓冲对象的属性"这半句不能用**（见下） |
| 透传链 `MachineSim.__init__ → _build_entities → SimWorld.run → run_gated → rollout` | ✅ 方向对，⚠️ 但**缺两处**：`run_gated:1796` 的"全关就退化成 `run()`"守卫，与 `SimWorld.run:1668` 的实际接线（见 §3.3） |
| 默认关 ⟹ 逐位不变 | ✅ 对，但要**加强成构造层面**（§3.4） |

**⚠️ 草图里唯一错的一处：优先级不能是"缓冲对象的属性"。** 三条理由：

1. **它在投递时刻冻结策略输入。** 策略要看到的是"**此刻**缓冲里有哪几件、机台什么状态"。
   按件属性存的话，优先级在 AGV 投递那一刻就算定了——那是**另一个时刻的状态**。
2. **它破坏候选打分的归一化。** 本仓骨架是"一组候选一次 softmax"（`_act` 一次前向、
   `log_softmax` 在候选维上）。逐件独立算分再比大小，**不是**一个概率分布：
   链 logp 没有正确的归约长度，`Decision.cand` 也就没有意义。
3. **它要动 item 的形状**（在四元组上挂第五个字段），于是 `des.py:485` **和** `des.py:543`
   两处解包都要改——"485 一行不改"的前提随之失效。

⟹ **改成"回调在取件那一刻，对当时的候选集打分"**（与 S/L/R/M/C/B 六头的契约同构）。

### 3.2 契约（写死）

```
Store 侧：  decide(mach: int, jobs: tuple[int, ...]) -> int      # 返回候选**序号**
机台侧：    MachineSim(..., seq=decide | None)
```

- **候选身份 = 缓冲内各件的作业号，按到达序**（与 `in_q.items` 同序）。
  机制侧把它交给 `algo/` 层；策略侧据此映射 token（§4.4）。
- **动作 = 候选序号**（`0..n-1`），与 R 头同型（"候选 = 路径，动作 = 候选序号"，
  `group_rel.py:842`）。序号而不是作业号的理由：**重复作业号在票面上仍有歧义**，
  而序号永远唯一；且 `_decision_logp_terms` 用 `cand.index(action)` 取回动作
  （`group_rel.py:1043`），序号是天然可 index 的。
- **只在 `n ≥ 2` 时调用回调。** `n == 1` 无可选（同 R/B 头的"候选 < 2 不记决策"纪律）。
  这条**由 Store 侧强制**，不由策略侧自觉。
- **非候选动作显式报错**（同其余六头的写法，`_make_pm_fn` 的形态）：静默回退会掩盖
  策略/候选集不一致。
- **LIFO（负载均衡）**：Store 容量语义不变（`Store._do_put` 只管 append + `len < capacity`），
  AGV 侧的"缓冲满则让步重试"循环（`des.py:1098` / `des.py:1254`）读 `len(in_q.items)`
  与 `in_q.capacity`——子类**必须**把 `capacity` 透传给 `super().__init__`，否则这两处静默变 `inf`。

### 3.4 关态 = 逐位不变（构造层面，不是"逻辑等价"）

**关态**（`seq_rank is None` **且** `policy_q is None`）：
`MachineSim.in_q` 是**裸 `simpy.Store`**，`_PriorityStore` 这个类**根本不出现**在对象图里。

这是最强形式的"默认关 ⟹ 逐位不变"：不是"子类忠实地做了同样的事"，而是**同一个类**。
判据可写成 `type(m.in_q) is simpy.Store`（关态），实现简单且不可辩驳。

⚠️ 不接受的做法：无条件把 `in_q` 换成 `_PriorityStore(decide=None)` 再在 `_do_get` 里
`if decide is None: return super()._do_get(event)`。行为等价，但把默认路径置于一个新类里，
把这个批次的回归面**人为放大**，且上面那条 `type()` 判据就写不出来了。

### 3.5 为什么 `seq_rank` **不进 `SimConfig`**

`op_choices` / `agv_phi` 是 `run()` 的**形参**（`des.py:1613`），不是 cfg 字段。同类对象同类处置：

1. 它是**实例规模**的数据（`n_jobs × n_ops`），不是运行时标度参数；
2. 进 `SimConfig` 就会进 `_cfg_key`（`des.py:232`）⟹ **参考运行缓存 `M_ref` 全部失效**，
   `f^ref` / `w` 要重算——一笔没必要的成本；
3. 进 cfg 就要同步进 `EvalSpec.from_cfg` / `check_same_dynamics`（`baselines/nsga2.py:102/122`），
   而那两处是**按名字枚举**动力学开关的 ⟹ 新增字段**不会被它们看见**（§60.4② 那类静默缺口）。

### 3.7 ⚠️ 实现前必须先核实的三个 SimPy 事实

本仓库历史上多次因"以为的 SimPy 语义"踩坑（§31 / §60）。动工前逐条核实：

1. **投递的件在 `_do_get` 被调用时已经在 `items` 里。**
   已核 4.1.2：`Put.__init__` 同步调 `_trigger_put` → `_do_put` → `items.append(item)`；
   `_trigger_get` 挂在 Put 事件的 `callbacks` 上，事件处理时才跑 ⟹ **在**。
   （仍建议实现后加一条断言测试，而不是只信本行。）
2. **`_do_get` 可能被同步调用在机台的进程帧里**（`Get.__init__` 里那次）
   也可能被调用在事件处理帧里（等着的时候件到了那次）。两条路径都要能取快照——
   `SimWorld.snapshot()` 是只读的、不 `yield`，两处都安全。
3. **同刻多件到达的次序由事件队列定**。⟹ 候选集 = "**取件这一刻已在缓冲里的**件"，
   不是"即将到来的"件。这是 (A) 的定义，不是缺陷，但**必须写进契约**（§2.5 的边界）。

## 4. 策略侧：排序头 **Q**

> 命名：六个头是 L/S/R/M/C/B，新头取 **Q**（queue）。开关名 `seq_head`（同 `pm_head` /
> `charge_head` / `batch_head` 的构词）。中文名统一用 **"排序头"**，决策名用 **"排序决策"**。

### 4.1 候选与动作

- **候选** = 此刻缓冲里的件，**按到达序**（0 = FIFO 队首）。
- **动作** = 候选序号（∈ `cand = (0, 1, …, n−1)`）。
- **候选有 token**——这是与 R/C/B 三头的**关键差别**：每个候选是一个**作业**，
  作业在 B 段**有自己的 token**（`build_tok` 的四段之一，`state_emb.py:256`）。
  ⟹ Q 头**逐候选**读该作业的 B token（与 S 头逐候选读机台 token 同型），
  **不是**像 C/B/R 那样全候选共用一行。
- **候选集由 `jobs`（DES 传入）与快照两侧同源**；两侧不一致即报错（§7 判据 6）。

### 4.2 决策特征（3 维）

| # | 量 | 口径 | 为什么 |
|---|---|---|---|
| 0 | `in_q_len / n_jobs` | 件数口径 | "还有多少件在等"。⚠️ **不用 `in_q_len / in_cap`**：② `finite_buffer` 关时 `in_cap = inf` ⟹ 该维**恒 0**（`pm_feat` 与 `machine_features` 的既有口径有这个退化，见 `state_emb.py:113`）。排序头的主题就是队列，不能让它在一整个消融组里变死维 |
| 1 | `backlog_min / ctx.total_work_min` | 工时口径（与 `_pm_cand_feat` 第 1 维同源） | 队列**还剩多少活**；与第 0 维互补（件数 vs 工时） |
| 2 | `now / ctx.m_ref` | 与 G 段 `time_progress` 同口径同截断 | episode 进度：越晚越该清空队尾 |

⚠️ **不设 `busy` 维**：排序决策只在机台**准备接件**时触发（`slot.count == 0` 恒成立）
⟹ 恒 0 的死维（同 `VehicleState.status` 的 `st_idle` 教训，§60.6）。

### 4.3 候选特征（4 维，逐槽钉）

| # | 槽 | 量 | 作用 |
|---|---|---|---|
| 0 | **换型** | `setup_flag(snap, mach, job, constraints)`（复用既有函数，`group_rel.py:226`） | ⑤ 的同作业连做（=0）比异作业（=2 min）便宜。**排序头的第一个真实收益**——(B) 之外只有 (A) 能在缓冲内实现它 |
| 1 | **交期** | `(due_j − now)/m_ref`，与 `job_features` 第 2 维**同式同截断** | TWT 的杠杆。⚠️ **⑧ `due_dates` 关时必须显式置 0**（同 `state_emb.job_features` 的守卫，`state_emb.py:146`）——照读 `JobState.due` 的 0.0 哨兵会得到 `(0−now)/m_ref`，报出一个不存在的紧迫度 |
| 2 | **剩余工时** | `JobState.remaining_min / ctx.total_work_min` | MWKR：长剩余先做，压 makespan |
| 3 | **队位** | `idx / max(n−1, 1)`（0 = FIFO 队首） | 唯一直接表达"离 FIFO 有多远"的维。没有它，头只能靠上文间接学到"队首是谁"；且这条维让"弃权回 FIFO"成为一个可表达的策略 |

**这四维让选择非平凡**：任何一件被扰动，行与行就不同（判据 4 逐槽测）。
**⑧/⑤ 关时的零化是"真值"不是哨兵**（同 `job_features` 的规约）。

### 4.4 token 下标（§31 同型陷阱，必须写进代码注释）

```
tok_idx[i] = n_m + jobs[i]        # M 段 + 作业号 = B 段行号
```

- **禁止**写成 `tok_idx = cand`：候选是**序号** `0..n-1`，照 S 头写会去读 **0..n-1 号机台的 M token**
  ——与 2026-10-04 修的 L 头缺陷、以及 M/C/B 三头的注释反复警告的形态**完全同型**（§31）。
- 建议：**照 `v_token_index`（`policy.py:37`）加一个对称的 `b_token_index(seg)`**，
  不硬编码 `n_m + job`。硬编码正是那条缺陷的来源。
- `Decision.mach` 记**决定方机台**（复用既有字段，同 M 头）：守卫测试据此知道该扰动哪一行。

### 4.6 开关与前置守卫

- **开关**：`seq_head=False`（默认）。
- **不需要**"某项约束必须开"的守卫——输入缓冲**任何配置下都存在**（与 ⑫/⑪/⑩ 不同型）。
- **需要**的是"机制不是死的"的证据：`seq_gets_ge2 > 0`（§7 判据 0 与判据 2）。
- **候选 < 2 不记决策**——由 Store 侧强制（§3.2）。

### 4.7 已知限度（如实写，不夸大）

1. **看不见未到的件**（§2.5）。
2. **不能闲置**（§2.5）——机器空转造成的损失它治不了。
3. **分差只来自候选特征 + 上下文**：token 部分是**每个候选自己的 B token**（比 C/B/R 三头多一路信号），
   但**没有加新的 token 类型**（不给"缓冲槽位"立 token）。要不要给缓冲槽位立 token 是**另一条机制**，本批不做。
4. **链长会增加**：每次"取件且 ≥2 件"多一个决策。增幅 = `seq_gets_ge2 ÷ (链长)`，
   **动工前先测**（判据 0）——⑩ 拼批头的教训（`mechanism-designs.md` §⑩：机会率 ≈ 0 ⟹ 机制是死的）。

## 5. 基线侧：外部工序顺序的注入（`seq_rank`）

### 5.1 为什么走 `run()` 而不是 `run_gated()`

NSGA-II 与规则基线走 `rollout(...)`（`nsga2.py:20` 明写"不用 `run_gated`：那是在线策略入口"）。
⟹ 排序入口**必须**在 `run()` 上，否则基线进不来。

```python
seq_rank[job][oi] -> int      # 越小越先；缺省/未覆盖的工序视为 +inf
```

- `run()` 侧把它编成一个**纯函数** `decide(mach, jobs)`：取 `rank[j][oi]` 最小的件，
  **同 rank 时取序号最小的（= FIFO 队首）**，保证确定性。
  （`oi` 从 `SimTrack.job_progress` 取，与 `_job_progress` 同源——**不新增记账**。）
- `run_gated()` 侧**只接 `policy_q`**，**不新增 `seq_rank` 形参**：静态优先级表天生是
  "只读快照的纯函数"，要在线路径用它，调用方包一个 `policy_q` 闭包即可
  （`policy_q` 的契约不要求它来自策略）。这样两条路径各自只有一个排序入口，**不存在"同传"的歧义**。

### 5.2 染色体 → 优先级的解码口径（写死）

标准 OS 解码：把 OS 串自左向右扫；第 k 次出现作业 j ⟹ `rank[j][oi=j 的第 k 道工序] = k`。
与 MS 段合成 `seq_rank`。**这是本仓唯一的解码口径**，基线侧与论文附录都要照它写。

### 5.3 ⚠️ (A) 不能精确复现外部计划（边界声明）

同 §2.5。论文必须写：**两边在同一个非延迟解码器下执行**；本仓的运输/故障/换型/交期
使"复现 HGS 的 makespan"不成立（§55.3(b)：这是**移植**，不是**评测**）。
§55.5 的警示继续有效：对拍数字**不得当 HGS 进论文**。

## 9. 开放问题（**未从代码解出**，须用户裁定或实测）

1. **机会率未知**（判据 0）。本仓有运输间接排序 ⟹ 缓冲可能经常只有 1 件。
   §55.2 的 223–356 是**HGS 自己的仿真器**的数字，**不能搬**（§58.3 已标）。
   若机会率 ≈ 0，本批的排序部分要**停手重议**（⑩ 的先例）。
2. **"等待时长"这一维要不要**。缓冲里的件**没有到达时刻**（item 是四元组，两处 put 都不带时间戳）。
   要加就要动 item 形状（两处解包 `des.py:485` / `des.py:543`）或新增一条跟踪量
   （`SimTrack`），且要在**两个投递点**写（`des.py:1102` / `1259`，漏一处即静默半错）。
   本设计**v1 不带这一维**，用"队位"（候选特征第 3 维）替代。要不要加，请裁定。
3. **优先级相等时的裁决**：本设计定"取序号最小（= FIFO 队首）"。
   若要改成"取序号最大"或随机，请明示（影响基线解码的确定性）。
4. **(B) 与 (A′) 的登记**：本批不做（§2.4）。若审稿人要求"精确执行外部计划"，再开一条。
5. **论文措辞**：本批之后不能说"我们优化 OS 编码"（§2.5 第 1 条）。
   论文里排序的定位句要怎么写（"机台队列重排" / "缓冲内优先级" / "在线排序"），请裁定。
6. **`in_q_len / n_jobs` vs `in_q_len / in_cap`**（§4.2 第 0 维）：本设计取前者（避免 ② 关时死维），
   与 `machine_features` 第 1 维的既有口径**不同**。要不要统一，请裁定。
7. **判据 5 的"无关机台 token"检验**在真编码器下不成立（注意力会跨 token 泄漏），
   必须用逐 token 恒等嵌入——这条已按 `test_charge_head` 的做法定死，但**是否需要额外的反向检验**
   （扰动决定方机台的 M token ⟹ 分数必变）未定：在恒等嵌入下它**不会**变（M token 不在头的输入里），
   故本设计**不写**这条判据。若评审要求，另议。
