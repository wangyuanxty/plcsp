### 69.7 下一步：**步 2 —— 重写流**（推式 → 批量派工）

**目的**：让 PA 的动作成为**真正的 (工件, 机台) 对**（两边都自由）—— 这是"PA 的动作空间能对上 AEI2025"的前提。

```
现在（推式）：  m₁ 完工 → transporter 挑 m₂ → 送 → 排队 → 加工
改后（批量）：  就绪集 = {前道刚完工、还没派机的工序}
                每个派工时刻：
                  PA 在 (就绪工序 × 机台) 里挑            ← 真正的对
                  LA 为被派的工序选车
                  送到 → 加工（无界缓冲）
```

**⚠️ 与 AEI2025 仍差一处**：他们**逐个**派，我们**一批**派（一批面对同一状态，逐个是序贯决策）。**要在论文里说明。**

### 69.8 ⚠️⚠️ 步 2 **做错了**：池子选错（2026-10-08，用户揪出）

**用户质问**："你的实现和 shi2025 一样吗？PA 不是选工序和机台吗？你仔细看了吗他们的规则？"

**回原文逐字核 —— 用户是对的。**

**原文**：

> *"The candidate actions for PA consist of nine composite dispatching rules that are used to **select an unfinished job** and **assign an appropriate machine to process the **earliest pending operation** of the selected job**."*
>
> *"the selection objects within PA's actions are limited to **the unfinished job** and the **candidate machines for the earliest pending operations** of the selected job"*

| | **AEI2025** | **我实现的（错）** |
|---|---|---|
| 池子 | **全体未完工工件**（含**正在加工的**） | "前道**刚**完工、待派机"的工序 |
| 池大小 | 开局 ~10（每未完工作业一项） | **实测平均 1.37**、最大 7 |
| 派工时机 | **提前**——工件还在前一台机上，下一道就派好机台了 | **就绪时**——前道完工才派 |
| 派到哪 | 写进**预留**（`plans`），transporter 据此执行 | 直接生成搬运任务 |

**⟹ 用户说的"选工序和机台"其实更准**：对**正在加工**的工件，它选的是**下一道工序**——那就是工序层面的选择。

**为什么这要紧**：我的池平均 1.37 ⟹ **PA 只有 ~12% 的决策有得挑** ⟹ **"PA 的动作是真正的 (工件, 机台) 对"这个目的**没达到****。

**而"提前派机"与"无限缓冲"是一条链**：派工提前 ⟹ 目标机台可能当时正忙 ⟹ 工件在**目的地缓冲里等** ⟹ 那正是无限缓冲的用途。

**⟹ 步 2 要重做**：

```
池 = { (j, oi) : j 未完工 且 plans[j][oi] 尚未定 }
     oi = 该作业的最早待加工工序（= done_ops[j]）
PA 在 (池 × 该工序的兼容机台) 里挑 → 写 plans[j][oi]（**预留**）
transporter 不变：读 plans 执行（离线路径）
```

**⚠️ 我的错因**：把"池"理解成了**就绪队列**（des 里的既有概念），而他们的池是**调度学意义上的未完工工件集**。**两个词都叫"池"，但不是一回事。**

### 70.2 契约变了（**这是本步的实质**）

```
步 2：policy_pa(snap, pool) -> 池下标           机台另走"最短加工时间"
步 3：policy_pa(view, pool) -> (池下标, 机台号)  机台由 PA 的复合规则定

**为什么必须一次返回两个**：复合规则是"**先**选工件、**后**给它的最早待加工工序配机台"
（AEI2025 原文的顺序）。分两次回调会看到**两个不同的状态**；同一批里前一件刚派走的预留，
后一次回调就看不见了。返回一对 ⟹ 工件的选择与机台的选择**共用同一份 `view`**。

**`online_s=True` 与 `policy_pa` 互斥（显式报错）**：两者都定机台，会互相覆盖同一格预留。

### 70.4 三处**与原文口径不同**，全部写进代码注释（不静默偏离）

| 处 | AEI2025 | 我们 | 为什么 |
|---|---|---|---|
| **平局** | **随机**选一个 | **确定性**：工件取池序最小、机台取机台号最小 | ① 逐位复现纪律；② 更要紧：**共享随机流里插一个新消费者会移位故障抽样** ⟹ "只改平局"变成"连扰动流都换了"，消融不干净 |
| **`MINU` 分子** | 已派工序加工时长之和（**计划**口径） | 累计**切削**工时 + 本批已派（**物理**口径） | 我们的 PA 是**提前预留**，照计划口径算会在"派工"与"入缓冲"之间**重复计** |
| **`EAM` 的 `avail_at`** | `MCT_k` = 已派工序最晚完工（**计划**口径） | `now + 在制剩余 + 缓冲积压`（**物理**口径） | 同上。另：本口径**不含**运输时长（派工时无从知道）⟹ `EAM` 略偏好远机台 |

`MINU` 的分母另立常量 `MINU_TIME_FLOOR = 1.0` min：
⚠️ **他们的 `MU_k = (Σ已派工时)/MCT_k(t)` 在"该机台从未派过活"时 `MCT_k = 0`——原文没写怎么处置，
那个点上定义是空的。** 取 1 min 地板使 `t = 0` 退化为"已记工时绝对值最小"，是该点上唯一有意义的读法。

### 70.5 ⭐ 批内投影（本步唯一不显然的设计）

`_pa_dispatch` **一次把池排空**（设计 §14.3 的"一批派"）。**同一批里仿真状态不变** ——
若规则只看静态快照，`EAM`/`MINU` 会给**整批**挑同一台机台，整批堆到一台机器上。
**那不是规则的本意，是"批量派工"这个流引入的假象。**

**修法**：`PAView.reserved(machine, proc)` 返回一份**把这次预留记进去**的新视图，
`_pa_dispatch` 每次派工后换新视图再继续 ⟹ 同批的后续派工看得到前面已派出去的活。

**跨批的在途预留不计**（只有本批的投影）：池在两次爆发之间通常只有 1–2 项，
而"哪些预留已入缓冲、哪些还在路上"要从 `queued_tasks` + `job_agv` 反推，
判据脆（在途 vs 已在输入缓冲**不可分辨**）⟹ 宁可少算，不引入会双计的口径。**登记为开放线索。**

### 70.8 ⚠️ 开放线索：**LA 的 Rule 3 在本仓的流下塌陷成 Rule 1**（登记，未解）

### 71.1 ⚠️ 那个"洞"是**真的**，不是理论上的

存在「已预留、但还没进目标机台缓冲」的调用 = 18 / 55      （33%）

```

**只看物理量的 `avail_at` / `busy_min` 在那 18 次决策上是瞎的** —— 机台头上已有的活看不见。

### 71.3 ❌ 唯一改不齐的一处：`MINU` 的分母

他们的 `MU_k = Σ已派工时 / MCT_k(t)`。**机台一件活都没派过时 `MCT_k = 0`** —— 除零。
**原文没写怎么处置。那个点上他们的定义是空的。**

是我没读原文、按"已完成"实现了它。**（卡没问题，是我没去核。）

### 74.4 ⚠️ 为什么"把池改大"**必须连带改触发点**（我推演过，不是猜）

改池的口径 **只差一行**（从 `done_ops` 改成"最低的未分配下标"）。**但改完就崩**：

1. 新口径下，池里每个工件的候选是**下一道未分配**的工序 ⟹ **池恒 ≈ 未完工工件数（~9），永不为空**；
2. 而 transporter 在**完工事件**上要读 `plans[j][done_ops]`——它**必须已被派**；
3. 若每次调用**只派一件**（原文的口径），PA 可能挑别的工件 ⟹ 轮到 X 时它的预留没有 ⟹ 读空；
4. 若**把池排空**（现状），因为池永不为空 ⟹ **一次调用就把整张调度表派完** ⟹ 荒谬。

**⟹ 在"完工驱动"的流里，池的口径与派的时机是**同一个问题**，不能只改一个。**

**而原文的流是**自驱动**的**：决策点 = "一道工序**被分配**的时刻" —— 派工本身产生下一个决策点，
**不是完工事件**。派工时 LA 立刻定车，运输任务**从派工那一刻就存在**（带一个**未来**的可运输时刻
`ct_{i,OP_i(t)}`），AGV 到点去取 ⟹ **这正是"车辆预留"**。

**⟹ 用户裁定的方向是对的，而且现在有了逐字依据。**

### 74.5 待办（本步的设计约束）

1. **池**：`{(j, oi) : j 未完工, oi = 最低的、plans[j][oi] is None 的下标}` —— **不再用 `done_ops`**；
2. **每次派工恰一件**（原文的口径），不排空；
3. **触发点从"完工"移到"派工"**：运输任务在派工那一刻创建，带 `ready_at` = 前道工序的预计完工时刻；
4. **LA 在同一个决策点定车**（照原文的 PA→LA 顺序），候选集带 `ready_at` ⟹
   **Rule 3 的"不晚于可运输时刻地最晚到达"恢复意义**（§70.8 的塌陷随之消失）；
5. **AGV 行为**：到取货点等件（件由源机台产出）——取件时机从 transporter 移到 AGV。

## 九十一、⭐⭐ 步 5b 的**机制层**：重放前缀（§4.2 靠它落地）（2026-10-09）

用户："为什么不能按照 v2 设计来做？" → **能。** §90 撤回"冲突"后，按 §4.2 的 ΔT 分段做。

### 91.1 机制：**帧不可复制 ≠ 不能重跑**

```
分支"g 在 Z_j 上"：
  ① 前缀（t=0 → Z_j）：**照 base 链的动作序列回放**（`ScriptedPolicy`，不调策略、不做前向）
  ② 接续（Z_j 起的 ΔT）：换成 `net` + **固定 g**（`BranchPolicy` 在第 j+1 个顶层点切换）
  ③ 停表：第 (j+1) 个顶层点一到就停（`run_gated(stop_after_ma=…)`）
```

**段回报 = 两条 `StepCounters` 累计读数相减**。**前缀一模一样 ⟹ 分支点的读数共享** ——
**这正是重放能成立的理由。**

### 91.2 ⭐ 硬证据：**回放逐位回到同一个 `Z_t`**

```
base Z1 : now=19.02  ops=20  jobs=1  E=1.2825  TWT=0.0
回放 Z1 : now=19.02  ops=20  jobs=1  E=1.2825  TWT=0.0   ← 逐位相同
```

**`now`/`ops`/`jobs`/`energy`/`TWT` 五项全对** ⟹ 重放确实回到了同一个状态。
**这是"用重放代替分叉"能成立的唯一判据**，已有断言钉住。

### 91.3 新增（都在 `env/des.py` 与 `hrl/`，**`des.py` 只加了两个小接口**）

| 件 | 作用 |
|---|---|
| `StepCounters`（des） | 顶层点的**累计读数**：`now / done_ops / done_jobs / energy_kwh / twt`（§10③ 的段回报取它的增量） |
| `run_gated(stop_after_ma=…)` | **停表**：跑到第 k 个顶层点就停（SimPy 事件，与 `done`/`horizon` 并联） |
| MA **在 t=0 也触发一次** | 否则**开局那 ΔT 个完工事件没有目标管**（§4.2 说"顶层每 ΔT 输出 g"） |

**差约 50 倍。** 来源：臂 B 的 `z(R)` 天生均值 0、标准差 1；
臂 A 的 `R − V(s_t)` 在 `V` 还没学好时**约等于 `R`（≈ −36）**。

**⚠️ 不改。** 理由：Adam 的更新是 `lr·m̂/(√v̂+ε)`，**对整体尺度因子近似不变** ⟹
两臂的**更新幅度可比**；而"学出来的基线 vs 组内基线"**本来就会带来尺度差**。
**但论文里必须写明**，否则审稿人会以为两个梯度范数差 50 倍是我漏了归一化。

**⚠️ 这条同时是一个开放线索**：若臂 A 跑起来明显发散/无进展，**先怀疑这里**，
再考虑加优势归一化（那会把"只差优势"变成"差两处"，要重新表述）。

### 98.4 ⑨ 的激活（§12.4 的"扰动下的最终业绩"）

`SimConfig.agv_mtbf` 默认 **480 min**，而 MK01 一局只有 ~100–170 min
⟹ **默认档下 ⑨ 几乎不发生**，"故障下稳不稳"就测了个空。
故最终评测用 `scaled_agv_mtbf(inst, target_failures=4.0)` ⟹ 实测 **`agv_mtbf` 480 → 56.90 min**。

### 98.5 `with_value` 的参数账（核对）

`n_params`：臂 A **605 021** / 臂 B **587 996** ⟹ 差 **17 025**。

## 九十九、⚠️⚠️ 用户问"为什么这么慢" —— **量出来的三条原因**（2026-10-09）

用户："为什么这么慢" / "模型在gpu上吗" / "为什么不用py312的环境？ gpu的"

**先认错**：Q1 的试跑我用了 `D:/anaconda/python.exe`（CPU 档）。`CLAUDE.md` 写着
**门禁**才必须 CPU 档，**"任何要 GPU 的测量"走 `py312`**。**Q1 是跑数，本就该用 py312。**

### 99.1 时间花在哪儿：**仿真免费，全在神经网络**

MK01 · τ=1.0 · `dt_events=20` · 一条链 **249 个决策**：

| 项 | 耗时 |
|---|---|
| **纯仿真**（不给任何策略，全走规则） | **0.018 s** |
| `build_tok`（249 次） | 0.053 s |
| **策略前向（249 次）** | **≈ 2.7 s** |
| 整条链 | ≈ 2.8 s |

**⟹ 仿真占 0.6%，前向占 99%。** 优化方向只有一个：**每次决策那一下前向**。

### 99.2 原因①：**`torch` 默认开 24 线程 ⟹ 反而慢 2.1 倍**

同一条链、3 次取中位，**两个解释器结果一致**：

| 线程数 | 默认解释器 | py312 |
|---|---|---|
| **24（torch 默认）** | **5.72 s** | 5.86 s |
| 1 | 3.35 s | 3.43 s |
| 4 | 2.97 s | 3.05 s |
| **8** | **2.70 s** | **2.84 s** |

**小张量（约 36 个 token × 128 维）被线程调度拖垮，不是算力不够。**
⚠️ **零成本，但只在跑数器里设**（`--threads`）——改线程数会改浮点归约的结合次序，
**门禁与既有读数依赖 CPU 默认档逐位不变**。

⚠️ **此处更正一处**：§98.1 记的"单条链 1.49 s"是**单次测量的噪声**（§98.2 的三次重复实测是 5.6–6.4 s）。
**那个数不可用。**

### 99.3 原因②：**v2 把设备档整个丢了**（已补）

```
grep -rn "cuda\|device" plcsp_v2/hrl/*.py    →  0 处命中
```

**v1 有一整套**：`policy.device` · `forward_enc` 的搬运 · `worker_device` · `ChainWorkerPool`。
**v2 重写时全丢了。** 后果：
- `NetPolicy._forward` 造的张量**恒在 CPU** ⟹ **模型永远跑在 CPU**，`--device cuda` 都没得选；
- 编码器里那条 **CUDA 图快路**（`_graph_ok` 的头一条就是 `tok_feat.is_cuda`）**永远触发不了**。

**已补**：`rollout.net_device()`（**设备跟随策略**，调用方只需 `net.to(device)`）·
`NetPolicy` 的 `self.device` 与 `torch.Generator(device=...)` · `train.batched_forward/logp_terms/ma_logp_at`
的搬运 · `q1_flat --device`（**CPU 档写 `cuda` 显式报错**，不静默降级）。
**CPU 档逐位不变**：`.to('cpu')` 是恒等操作，`torch.Generator(device='cpu')` 与旧写法逐位相同（v1 同口径）。

### 99.4 ⚠️ 原因③（**但结论是"GPU 治不了"**）：补上设备档以后，GPU **并不快**

`py312` · RTX 4060 Laptop · 同一条链：

| 设备 | 整条链 | 每决策 | CUDA 图 |
|---|---|---|---|
| CPU | 5.94 s | 23.85 ms | 0 张 |
| **CUDA** | **3.37 s** | 13.53 ms | 1 张 ✓ |

**CUDA 3.37 s，比 CPU 8 线程的 2.84 s 还慢。**

**为什么**：这个负载是**每次只算一条**（B=1）、**延迟受限**。GPU 的并行度用不上，
而每条决策要做 **3–4 次设备同步**（取动作、取 logp、判补零列）。
**⟹ GPU 治不了"每次一条"。** 这条要记住，别再往 GPU 上使劲。

（CUDA 图**确实建起来了**（1 张），说明补的设备档是有效的 —— 只是收益抵不过同步开销。）

### 99.5 ⭐ 真正该修的是原因③：**8 条链在排队跑，32 个核闲着 31 个**

`flat_step(n=8)` 的 8 条链**互相独立**，现在却在**一个进程里顺序跑**。
**v1 为此有 `ChainWorkerPool`（多进程并行跑链）—— v2 也丢了。**

| 做法 | 估算 |
|---|---|
| 现状（24 线程，顺序 8 条） | ≈ 46 s/步 |
| 只设 8 线程 | ≈ 22 s/步（2.1×） |
| **+ 多进程并行 8 条链**（每条 1 线程） | **≈ 3–4 s 起 + 重算** ⟹ 估算 **10–12 s/步** |

**⟹ 合计约 4×。** 这比"换 GPU"大得多，而且是 v2 欠的账。

**⏸ 未做**：worker 池要新写（`multiprocessing` + `spawn` + 把 `Decision` 序列化回主进程）。
⚠️ **它会带来一个要写明的口径**：并行档每进程 1 线程 ⟹ 浮点归约次序与单进程档不同
⟹ **末位可能不同**。两臂**必须同档**，且**报出的数字要注明跑在哪个档**。
