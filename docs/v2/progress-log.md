### 69.7 下一步：**步 2 —— 重写流**（推式 → 批量派工）

**目的**：让 PA 的动作成为**真正的 (工件, 机台) 对**（两边都自由）—— 这是"PA 的动作空间能对上 AEI2025"的前提。

```
现在（推式）：  m₁ 完工 → transporter 挑 m₂ → 送 → 排队 → 加工
改后（批量）：  就绪集 = {前道刚完工、还没派机的工序}
                每个派工时刻：
                  PA 在 (就绪工序 × 机台) 里挑            ← 真正的对
                  LA 为被派的工序选车
                  送到 → 加工（无界缓冲）
```

**⚠️ 与 AEI2025 仍差一处**：他们**逐个**派，我们**一批**派（一批面对同一状态，逐个是序贯决策）。**要在论文里说明。**

### 69.8 ⚠️⚠️ 步 2 **做错了**：池子选错（2026-10-08，用户揪出）

**用户质问**："你的实现和 shi2025 一样吗？PA 不是选工序和机台吗？你仔细看了吗他们的规则？"

**回原文逐字核 —— 用户是对的。**

**原文**：

> *"The candidate actions for PA consist of nine composite dispatching rules that are used to **select an unfinished job** and **assign an appropriate machine to process the **earliest pending operation** of the selected job**."*
>
> *"the selection objects within PA's actions are limited to **the unfinished job** and the **candidate machines for the earliest pending operations** of the selected job"*

| | **AEI2025** | **我实现的（错）** |
|---|---|---|
| 池子 | **全体未完工工件**（含**正在加工的**） | "前道**刚**完工、待派机"的工序 |
| 池大小 | 开局 ~10（每未完工作业一项） | **实测平均 1.37**、最大 7 |
| 派工时机 | **提前**——工件还在前一台机上，下一道就派好机台了 | **就绪时**——前道完工才派 |
| 派到哪 | 写进**预留**（`plans`），transporter 据此执行 | 直接生成搬运任务 |

**⟹ 用户说的"选工序和机台"其实更准**：对**正在加工**的工件，它选的是**下一道工序**——那就是工序层面的选择。

**为什么这要紧**：我的池平均 1.37 ⟹ **PA 只有 ~12% 的决策有得挑** ⟹ **"PA 的动作是真正的 (工件, 机台) 对"这个目的**没达到****。

**而"提前派机"与"无限缓冲"是一条链**：派工提前 ⟹ 目标机台可能当时正忙 ⟹ 工件在**目的地缓冲里等** ⟹ 那正是无限缓冲的用途。

**⟹ 步 2 要重做**：

```
池 = { (j, oi) : j 未完工 且 plans[j][oi] 尚未定 }
     oi = 该作业的最早待加工工序（= done_ops[j]）
PA 在 (池 × 该工序的兼容机台) 里挑 → 写 plans[j][oi]（**预留**）
transporter 不变：读 plans 执行（离线路径）
```

**⚠️ 我的错因**：把"池"理解成了**就绪队列**（des 里的既有概念），而他们的池是**调度学意义上的未完工工件集**。**两个词都叫"池"，但不是一回事。**

### 70.2 契约变了（**这是本步的实质**）

```
步 2：policy_pa(snap, pool) -> 池下标           机台另走"最短加工时间"
步 3：policy_pa(view, pool) -> (池下标, 机台号)  机台由 PA 的复合规则定
```

**为什么必须一次返回两个**：复合规则是"**先**选工件、**后**给它的最早待加工工序配机台"
（AEI2025 原文的顺序）。分两次回调会看到**两个不同的状态**；同一批里前一件刚派走的预留，
后一次回调就看不见了。返回一对 ⟹ 工件的选择与机台的选择**共用同一份 `view`**。

**`online_s=True` 与 `policy_pa` 互斥（显式报错）**：两者都定机台，会互相覆盖同一格预留。

### 70.4 三处**与原文口径不同**，全部写进代码注释（不静默偏离）

| 处 | AEI2025 | 我们 | 为什么 |
|---|---|---|---|
| **平局** | **随机**选一个 | **确定性**：工件取池序最小、机台取机台号最小 | ① 逐位复现纪律；② 更要紧：**共享随机流里插一个新消费者会移位故障抽样** ⟹ "只改平局"变成"连扰动流都换了"，消融不干净 |
| **`MINU` 分子** | 已派工序加工时长之和（**计划**口径） | 累计**切削**工时 + 本批已派（**物理**口径） | 我们的 PA 是**提前预留**，照计划口径算会在"派工"与"入缓冲"之间**重复计** |
| **`EAM` 的 `avail_at`** | `MCT_k` = 已派工序最晚完工（**计划**口径） | `now + 在制剩余 + 缓冲积压`（**物理**口径） | 同上。另：本口径**不含**运输时长（派工时无从知道）⟹ `EAM` 略偏好远机台 |

`MINU` 的分母另立常量 `MINU_TIME_FLOOR = 1.0` min：
⚠️ **他们的 `MU_k = (Σ已派工时)/MCT_k(t)` 在"该机台从未派过活"时 `MCT_k = 0`——原文没写怎么处置，
那个点上定义是空的。** 取 1 min 地板使 `t = 0` 退化为"已记工时绝对值最小"，是该点上唯一有意义的读法。

### 70.5 ⭐ 批内投影（本步唯一不显然的设计）

`_pa_dispatch` **一次把池排空**（设计 §14.3 的"一批派"）。**同一批里仿真状态不变** ——
若规则只看静态快照，`EAM`/`MINU` 会给**整批**挑同一台机台，整批堆到一台机器上。
**那不是规则的本意，是"批量派工"这个流引入的假象。**

**修法**：`PAView.reserved(machine, proc)` 返回一份**把这次预留记进去**的新视图，
`_pa_dispatch` 每次派工后换新视图再继续 ⟹ 同批的后续派工看得到前面已派出去的活。

**跨批的在途预留不计**（只有本批的投影）：池在两次爆发之间通常只有 1–2 项，
而"哪些预留已入缓冲、哪些还在路上"要从 `queued_tasks` + `job_agv` 反推，
判据脆（在途 vs 已在输入缓冲**不可分辨**）⟹ 宁可少算，不引入会双计的口径。**登记为开放线索。**

### 70.8 ⚠️ 开放线索：**LA 的 Rule 3 在本仓的流下塌陷成 Rule 1**（登记，未解）

### 71.1 ⚠️ 那个"洞"是**真的**，不是理论上的

```
存在「已预留、但还没进目标机台缓冲」的调用 = 18 / 55      （33%）

```

**只看物理量的 `avail_at` / `busy_min` 在那 18 次决策上是瞎的** —— 机台头上已有的活看不见。

### 71.3 ❌ 唯一改不齐的一处：`MINU` 的分母

他们的 `MU_k = Σ已派工时 / MCT_k(t)`。**机台一件活都没派过时 `MCT_k = 0`** —— 除零。
**原文没写怎么处置。那个点上他们的定义是空的。**

是我没读原文、按"已完成"实现了它。**（卡没问题，是我没去核。）

### 74.4 ⚠️ 为什么"把池改大"**必须连带改触发点**（我推演过，不是猜）

改池的口径 **只差一行**（从 `done_ops` 改成"最低的未分配下标"）。**但改完就崩**：

1. 新口径下，池里每个工件的候选是**下一道未分配**的工序 ⟹ **池恒 ≈ 未完工工件数（~9），永不为空**；
2. 而 transporter 在**完工事件**上要读 `plans[j][done_ops]`——它**必须已被派**；
3. 若每次调用**只派一件**（原文的口径），PA 可能挑别的工件 ⟹ 轮到 X 时它的预留没有 ⟹ 读空；
4. 若**把池排空**（现状），因为池永不为空 ⟹ **一次调用就把整张调度表派完** ⟹ 荒谬。

**⟹ 在"完工驱动"的流里，池的口径与派的时机是**同一个问题**，不能只改一个。**

**而原文的流是**自驱动**的**：决策点 = "一道工序**被分配**的时刻" —— 派工本身产生下一个决策点，
**不是完工事件**。派工时 LA 立刻定车，运输任务**从派工那一刻就存在**（带一个**未来**的可运输时刻
`ct_{i,OP_i(t)}`），AGV 到点去取 ⟹ **这正是"车辆预留"**。

**⟹ 用户裁定的方向是对的，而且现在有了逐字依据。**

### 74.5 待办（本步的设计约束）

1. **池**：`{(j, oi) : j 未完工, oi = 最低的、plans[j][oi] is None 的下标}` —— **不再用 `done_ops`**；
2. **每次派工恰一件**（原文的口径），不排空；
3. **触发点从"完工"移到"派工"**：运输任务在派工那一刻创建，带 `ready_at` = 前道工序的预计完工时刻；
4. **LA 在同一个决策点定车**（照原文的 PA→LA 顺序），候选集带 `ready_at` ⟹
   **Rule 3 的"不晚于可运输时刻地最晚到达"恢复意义**（§70.8 的塌陷随之消失）；
5. **AGV 行为**：到取货点等件（件由源机台产出）——取件时机从 transporter 移到 AGV。

## 九十一、⭐⭐ 步 5b 的**机制层**：重放前缀（§4.2 靠它落地）（2026-10-09）

用户："为什么不能按照 v2 设计来做？" → **能。** §90 撤回"冲突"后，按 §4.2 的 ΔT 分段做。

### 91.1 机制：**帧不可复制 ≠ 不能重跑**

```
分支"g 在 Z_j 上"：
  ① 前缀（t=0 → Z_j）：**照 base 链的动作序列回放**（`ScriptedPolicy`，不调策略、不做前向）
  ② 接续（Z_j 起的 ΔT）：换成 `net` + **固定 g**（`BranchPolicy` 在第 j+1 个顶层点切换）
  ③ 停表：第 (j+1) 个顶层点一到就停（`run_gated(stop_after_ma=…)`）
```

**段回报 = 两条 `StepCounters` 累计读数相减**。**前缀一模一样 ⟹ 分支点的读数共享** ——
**这正是重放能成立的理由。**

### 91.2 ⭐ 硬证据：**回放逐位回到同一个 `Z_t`**

```
base Z1 : now=19.02  ops=20  jobs=1  E=1.2825  TWT=0.0
回放 Z1 : now=19.02  ops=20  jobs=1  E=1.2825  TWT=0.0   ← 逐位相同
```

**`now`/`ops`/`jobs`/`energy`/`TWT` 五项全对** ⟹ 重放确实回到了同一个状态。
**这是"用重放代替分叉"能成立的唯一判据**，已有断言钉住。

### 91.3 新增（都在 `env/des.py` 与 `hrl/`，**`des.py` 只加了两个小接口**）

| 件 | 作用 |
|---|---|
| `StepCounters`（des） | 顶层点的**累计读数**：`now / done_ops / done_jobs / energy_kwh / twt`（§10③ 的段回报取它的增量） |
| `run_gated(stop_after_ma=…)` | **停表**：跑到第 k 个顶层点就停（SimPy 事件，与 `done`/`horizon` 并联） |
| MA **在 t=0 也触发一次** | 否则**开局那 ΔT 个完工事件没有目标管**（§4.2 说"顶层每 ΔT 输出 g"） |

**理由（用户给的，我同意）**：这个负载 `batch=1`（§99.5 已量）——**每次只算一条、延迟受限**，

### 102.2 ⭐ 新增臂 **A2**：critic + 优势归一化（`hrl/flat.py`）

**为什么必须有它**（§101.4）：臂 A 的优势尺度与 B 差 ~50 倍（`grad_norm` 10527 vs 199），
标准 PPO 的 `(A − μ)/σ` **我们故意没做**。**没做归一化的 critic 臂发散，说明不了 critic 没用。**

| 臂 | 优势 | critic | 归一化 |
|---|---|---|---|
| `A` | `R − V(s_t)` | 有 | **无** |
| ⭐ `A2` | `R − V(s_t)` | 有 | **有**（标准 PPO） |
| `B` | `z(R)` | 无 | 有（自带） |

**A2 的归一化口径**：`Â = (A − μ_A)/(σ_A + ε)`，**在整组更新的全部决策上算** ——
标准 PPO 的 minibatch 归一化在这里对应的就是"这一组"。

⚠️ **不改 B**。B 的 `z(R)` 天生均值 0、标准差 1，已经归一化过。
**两臂都归一化 ⟹ 差异仍然只是"基线从哪来"。**

**实现**：`ARMS = ("A","A2","B")` · `CRITIC_ARMS` · `NORM_ARMS` 三个常量分开写，
`flat_step` 先收集全部 `(adv, lp)` 再整组归一化（**不能逐链归一化** ——
那会把"哪条链更好"这条跨链信息整条抹掉，而那正是组内相对法赖以工作的东西）。

**验收**：`test_a2_pulls_the_advantage_scale_back_to_b` —— 用 `grad_norm` 的**比值**做判据
（比值对机器快慢不敏感）：`A/B > 10` 且 `A2/B < 5`。**10 passed。**

## 一百〇六、段池落地：**正确性已验收，加速比受降频机器所限（2.3×）**（2026-10-09）

### 106.1 做了什么

`hrl/pool.py` 新增 **`SegmentPool`** —— 与 `ChainPool` 同一套模式，任务粒度为**段**：

| | |
|---|---|
| `_seg_worker` | 子进程跑**一批段**（`(state, spec, with_value, jobs)`） |
| `_chunk_round_robin` | **轮转**分块 —— 段的成本随 `j` 涨（前缀越长），连续切块会让最后一块独占大半时间 |
| 回填 | 按**记录的原下标**复位（**不能靠比对 job 内容** —— 两条段可以逐字段相同） |
| `train._run_segments` | `pool=None` 就地跑 / 给了就走池；**两条路产出同形的 `Branch`** |
| 接线 | `phase_b` / `phase_a` / `train_step` 全加 `pool=` 透传 |

⚠️ **按批送 `state_dict`**（不是一个任务一条段）：约 2.4 MB，逐条送 400 条段要近 1 GB；按 `n_workers` 批送只要 ~40 MB。

**⚠️ 容差不是逐位**：并行档每进程 1 线程，浮点归约次序与父进程不同。

不是 2.3× —— 2.3× 是**整步**的比值，被串行部分摊薄了。**两个数都对，但说的是不同的事。**

### 107.2 ⭐ 两种负载要两种线程数（同一进程里）

**§99.2 与本次扫描给出了相反的方向，因为它们是两类负载：**

| 负载 | 形状 | 最优线程 |
|---|---|---|
| **rollout / `base_chain` / 段** | **每次一条**决策的串行链（延迟受限） | **1**（24 线程慢 2.7×） |
| **`logp` 前向 + backward** | **一大批**（~2880 条决策）矩阵运算（吞吐受限） | **8**（比 1 线程快 2.9×） |

**⟹ `train_step` 改成按阶段切线程**：`base_chain` 前设 1，阶段 + `backward` 用 `loss_threads`（默认 8），
`finally` 复位。⚠️ **只在带池时切** —— `pool=None` 时段也在父进程跑（属第一类），多线程反而更慢。

**顺手否掉一条**（省得做无用功）：**"把 96 次逐分支 `logp` 合并成一次"没有收益** ——
实测 4481 ms vs 4368 ms，**1.0×**。batch=30 时开销可忽略，这个算子本来就是计算受限的。

### 107.3 端到端实测

```
顺序档（1 线程）              16.3 s/步
池 16 进程 · loss_threads=8    5.6 s/步     ⟹ 2.9×
池 16 进程 · loss_threads=1    6.2 s/步
```

⚠️ **多线程只多给 10%，比预测的少。**
预测是"串行 3.85 → 1.10 s"（按独立基准的 2.9× 推），实际只降了 0.6 s。

**原因**：**降频机器上，父进程开 8 线程会和 16 个 worker 抢**。
**⟹ 这个权衡在健康机器上会不同，必须重测。**

### 107.4 修正后的账（⚠️ 仍全是降频机器的读数）

| | 全串行 | 段池 + 8 线程 |
|---|---|---|
| mk01 `train_step` | 16.3 s/步 | **5.6 s/步** |
| 10 实例（×31，v1 比例，待重测） | 505 s/步 | **~174 s/步** |

## 一百〇八、⭐ D5 跑数器：**扁平链 vs 两层**（2026-10-09）

### 108.1 问的是什么

**分层（我们的两层 + 交替）值不值那个代价？**

| 臂 | 怎么训 | 组 | 更新 |
|---|---|---|---|
| **`flat`** | `flat_step(arm="B")` —— 一条链的**全部**决策算**一个**组 | 共享 | 同步 |
| **`two`** | `train_step` —— 按层切成两个组 | 分层 | **交替** |

**两臂同一套网络、同一个仿真、同一个 `n=8`、同 `dt_events`。差别只在"组怎么切、怎么更新"。**

### 108.2 ⚠️ D5 与 Q2（实验计划 D2）**几乎是同一件事**

设计 §12.0 已核：**「分层组 + 同步」不可行**（同步要付 `N×M` = 64T）⟹
**能比的只有「扁平分同步」vs「分层交替」。**

**⟹ 而这两个臂都已有代码**（`flat.py` / `train.py`）—— **所以先做 D5，不用新写臂。**
Q2 那个"共享组"臂（组内同时变目标与执行）仍待写，但它与 `flat` 的差别更小。

### 108.3 ⚠️ 报数时必须**一并报机时**

**两臂的每步成本不同**（设计 §12.3：分层是 1× vs 2×）。
同一 `--steps` 下两臂花的机时不一样 ⟹ **"谁更好"分不清是不是"谁跑得多"。**

实测（降频机 · 16 进程）：`two` ≈ 5.6 s/步 · `flat` ≈ 5.2 s/步 —— **并不正好是 2×**，
因为两层的段是短的（ΔT），而扁平的链是整条（249 决策）。**如实记，别套设计的 1×/2×。**

### 108.4 两臂的返回**不同构** —— 如实记，不用零顶替

```
flat_step → {"loss", "r_mean", ...}
train_step → {"base_makespan", "B": {...}, "A": {...}}
```

跑数器按各自有的字段记（`loss`/`r_mean` vs `loss_B`/`loss_A`/`n_top`/`seg_std_A`）。
**不拿零顶替** —— 那会让"没这个量"看起来像"这个量是 0"。

### 108.5 冒烟（`n=4`、`dt_events=50`、各 2 步）✅

```

two step 2  base_ms=188.7  loss_B=-817.0  loss_A=0.0  n_top=5  seg_std_A=[0,0,0,0,0]
```

**⚠️ `loss_A ≡ 0` 且 `seg_std_A` 全零 —— 这正是 §89.2 预期的**（`B` 零初始化时阶段 A 拿不到信号），
**不是 bug。** 这条同时验证了：**阶段 A 的空转在真链上确实发生**。

## 一百〇九、⭐ D1 跑数器：**关掉 `g`**（目标条件化到底起没起作用）（2026-10-09）

### 109.1 问的是什么 —— **v2 的核心主张**

> 「MA 顶层出 `g`，下层条件在 `g` 上」**有用**

`design.md` §11 已核：v2 **逐件看没有一件是新的**，创新性靠**组合**。
**⟹ 组合的价值必须由实验证明。D1 就是那条实验。**

### 109.2 ⚠️ 一个已核的陷阱：**必须训练后**再测

**`B` 零初始化 ⟹ 起始时 `g` 完全不影响任何动作**（§93/§95）。
**⟹ 在未训练的网上"关掉 `g`" ≡ "本来就没开" ⟹ 测不出任何东西。**

**⟹ D1 做成「拿一个训好的模型做评测消融」，不是重训。** 便宜，而且绕开陷阱。

### 109.3 五个变体（同一个模型，只改 `g` 怎么来）

| 变体 | `g` 从哪来 | 问题 |
|---|---|---|
| **`free`** | **MA 每步自采**（正常） | 基线 |
| `fixed_111` | 冻结中档 `(1,1,1)` | 「顶层关掉，给个不变的 `g`」 |
| `fixed_000` / `fixed_333` | 冻结在两端的角 | 同上，`g` 取极端值 |
| **`b_zero`** | **四个 `B` 置零** | 「`g` **完全**断开」 |

**判据**：

| 结果 | 结论 |
|---|---|
| **`free` ≈ 各 `fixed_*` / `b_zero`** | ⚠️ **`g` 没起作用 —— 顶层是装饰** |
| **`free` 明显更好** | ✅ 目标条件化有贡献 |
| 各 `fixed_*` 之间**差很多** | ✅ `g` 是有语义的方向，不是随便一个常数 |

⚠️ **`b_zero` 是"分布外"读法**：模型在 `B≠0` 下训，归零会让下层 logits 整体偏移 ⟹
**掉分可能来自"没见过"，不只是"少了 `g`"。它是旁证，不是主判据**（主判据是 `free` vs `fixed_*`，两者都在分布内）。

### 109.4 ⭐ 冒烟**实证**了那个陷阱

拿一个**只跑了 2 步**的检查点（`B ≈ 0`）跑五个变体：

```
free       ms=57.14  twt=195.56  R=-10.842   MA 决策 6 条
fixed_000  ms=57.14  twt=195.56  R=-10.842   MA 决策 0 条
fixed_111  ms=57.14  twt=195.56  R=-10.842   MA 决策 0 条
fixed_333  ms=57.14  twt=195.56  R=-10.842   MA 决策 0 条
b_zero     ms=57.14  twt=195.56  R=-10.842   MA 决策 6 条
```

**五个变体逐位相同** —— 因为 `B` 还接近零。**这就是陷阱的实证，不是推理。**

（`free`/`b_zero` 记到 6 条 MA 决策、`fixed_*` 是 0 条 ⟹ 冻结那条路对。）

### 109.5 顺带：MA 采到的档会被记下来

`free` 变体顺带输出 **MA 实际采到的档**（`ma_bins`）—— 「顶层学到了偏好哪一档」
**本身是 D6（读出 `B` 矩阵）的一半**，而这一半是免费的。

D1 **不重训**，直接用 `checkpoints/d5/` 下 `--save-dir` 存的模型（§108.6 已带）。

## 一百一十三、⚠️ 两次自我更正 + 一条真发现：**⑨ 的故障 83–97% 发生在 AGV 空闲时**（2026-10-09）

### 113.1 ⚠️ 更正一：**不多。我把小样本噪声当成了异常**

mk08 · `agv_mtbf=480` · 一局 638 min · 3 AGV ⟹ 期望 `3 × 638 / 480 = 3.99` 次/局。

**单条扰动流实测 8 次** ⟹ 我报成"是期望的 2 倍"。

```
期望 3.98
实测/期望 0.98          ⟹ 完全吻合
```

**⟹ 8 次只是 +1.8σ（sd=2.29）。我不该拿单条流下结论 —— 泊松计数在小 n 上噪声本就大。**
（`agv_mtbf` 换 960 / 1920 时实测 5 / 2，期望 2 / 1 —— 也在同一量级的噪声内。）

### 113.2 ⚠️ 更正二：一列读数**作废**

我报了"AGV 空驶/载货/空闲**时长**占比 = 0% / 0% / 100%"。
**那是我读错了键名** —— `agv_empty_min` / `agv_loaded_min` **不在 `run_gated` 的返回里**，
`m.get(key, 0)` 静默取成 0，于是被算成"空闲 100%"。**那一列作废。**

### 113.3 ⭐ 真发现：**故障的 83–97% 发生在 AGV 空闲时**

**⟹ ⑨ 的两条"复杂路径"几乎不被触发：**

## 一百一十四、⭐ 修掉一个**我引入的**实现问题：段池被每顶层点调一次（2026-10-09）

用户："神经网络的前向不是时间占比很小吗？" + "是不是我们的实现有问题，导致仿真太耗时？看看别人开源的怎么做的"

### 114.1 ⚠️ 先更正我自己的说法：**仿真不是瓶颈，"段"里主要是前向**

我前面把 `train_step` 的「段」笼统说成"仿真"—— **不准确**。§99 实测（MK01 一局）：

| | 耗时 |
|---|---|
| **纯仿真**（规则驱动、无策略） | **0.018 s** |
| 带策略（249 次前向） | **3.0 s** |
| `build_tok`（快照 → token，249 次） | 0.053 s |

**⟹ 仿真占 0.6%，前向占 99%。`build_tok` 只占每次决策的 3%。**
**用户那句"前向占比很小"是反过来的 —— 前向是**绝大**部分。**（用户问的是反问，答案是"不小，它就是大头"。）
⚠️ **"仿真太耗时"这个假设不成立。**

### 114.2 别人的开源实现（`third_party/`，33 个克隆）

| 仓库 | 环境文件 | 行数 |
|---|---|---|
| **L2D**（经典基准） | `JSSP_Env.py` | **128** |
| **fjsp-gnnrl** | `fjsp_env.py` | **145** |
| `End-to-end-DRL-for-FJSP` | `FJSP_Env.py` | 331 |

**范式不同**：他们是**数组步进式**（numpy 状态数组 + `step()` 更新）；我们是**事件驱动 DES（SimPy）**。
**⚠️ 但我们的纯仿真只有 0.018 s/局 ⟹ SimPy 不是瓶颈。范式差异不构成速度问题。**

**⟹ "别人开源怎么做"的答案：他们的环境小、状态是数组；但这不是我们慢的原因。**

### 114.3 ⭐ 真问题：`SegmentPool` 被**每个顶层点**调一次

`_run_segments` 原来是**每顶层点一次池调用**：

```
phase_b:  for j in range(n_top): _run_segments(...)     ← n_top 次 map
phase_a:  for j in range(n_top): _run_segments(...)     ← n_top 次 map
```

而 `SegmentPool.segments()` **每次调用都要把 `state_dict`（2.4 MB）发给每个 worker** ⟹

```
每步序列化量 = 2 × n_top × n_workers × 2.4 MB
dt_events=10（n_top=38，16 进程）⟹ 每步 ~2.9 GB
```

**修法**：`_run_all_segments` —— **同一阶段的全部顶层点的段合成一次调用**，返回值按 plan 边界切回。
**合并调用不改读数**（段互相独立且确定），只改谁在哪个 worker 上跑。

**实测：**

| `dt_events` | `n_top` | 段数 | 修前 s/步 | **修后 s/步** | 提速 |
|---|---|---|---|---|---|
| 10 | 38 | 608 | 31.1 | **21.7** | 1.43× |
| 20 | 25 | 400 | 25.8 | **18.9** | 1.37× |
| 40 | 22 | 352 | 25.0 | **19.1** | 1.31× |
| 80 | 17 | 272 | 22.4 | **16.6** | 1.35× |

**测试套件 29.2 s → 17.76 s（1.6×）。**

### 114.4 ⚠️ 更正：`dt_events` **不是"只动 `n_top`"的干净旋钮**

我上一条说"它是唯一干净旋钮"—— **错了**。`dt_events` ↑ ⟹ `n_top` ↓ **但同时每段变长**（ΔT 变大）
⟹ 两者互相抵消 ⟹ **拟合不出干净的指数**（修后裸指数 0.33，且 dt=40 反常：段更少反而更慢）。

**⟹ "换大实例要多久"目前只能给保守范围，不能给一个指数。**
