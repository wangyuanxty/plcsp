⚠️ **一条运维注意（2026-10-05 实测栽过）**：**别改正在执行的壳脚本**。bash **按需增量读**
脚本文件；重写一个已在跑的脚本（哪怕只改注释、只是让内容变长）会让运行中的实例从**新的
字节偏移**接着读，轻则读到乱码行，重则 `unexpected EOF` 当场退出。实测：接力脚本被重写后
直接死掉，4 个 run 没起跑。**要改就先停它，或另写一个新文件。**

⚠️ **第二条运维注意（2026-10-05 观察到）**：**等待要设超时，且别让多个 agent 各挂一个轮询等同一件事。**
实测同时有 **4–5 个壳**用三种写法（`sleep 300` / `while ! grep …; do sleep 30` /
`deadline=$((SECONDS+570))`）挂在**同一个**门禁日志上等 `EXIT=`。
**其中 `while ! grep …; do sleep 30; done` 没有超时**——被等的东西若永远不写那个标记，
它会**无限循环**（与"任务 killed 但进程没死"是同类坑，本仓栽过三次）。
**纪律**：① 轮询一律带 `deadline` 或 `timeout`；② **同一件事只留一个等待者**。
（无害但浪费：不占 CPU，只是让进程表变脏、让人分不清哪些是正事。）

- T3 的 `check_influenceable`（`env/t3_budget.py`）：keep 含 ⑫ 要 `pm_head`、含 ③ 要 `pm_head`+役龄、
  含 ⑪ 要 `charge_head`。**约束关掉后策略没有作用手段**，T3 再罚它就是罚不可控的事
  （与 ④⑨ 不纳入 T3 同一条理由）。
- T3 **只支持 `adv_mode='scalar'`**（`algo/group_rel.py` 入口显式报错）——罚项加在标量奖励上、
  组内 z 化之前。"罚项算在哪一项"在 `per_objective` / `reinforce` 口径下没有定义（v1 未实现）。

⟹ **T3 的 keep 是机制开关的确定函数，不是自由变量**：`keep = 六条可控约束 ∩ 该 run 仍开的约束`。
这条要写进论文。故第 2/3/5/6/9/10 个 run 与 `full` 的差异**不止一项**——但多出的每一项都是守卫强制的，
不是另选的。**报消融表时必须写出实际开关集**，不能只写"关掉 X"。

**惰性开关**：`--agv-failover` 在 ⑨ 关时车从不 down ⟹ 真惰性（协调者核过代码），照基线传。
**`--multi-drop` 在 ⑩ 关时不是惰性**——见 §9.7.1（实测）。

#### 9.7.1 `multi_drop` 在 ⑩ 关时**不是**惰性开关（2026-10-05 实测）

**判据**：`c-none` 这个 run（⑩ 关 ⟹ `AgvSim.capacity ≡ 1`）带 / 不带 `--multi-drop` 各跑 2 步，
同 seed、同并发模式、同设备。

| 步 | `r`（带） | `r`（不带） |
|---|---|---|
| 0 | −10.954 | −11.456 |
| 1 | −11.447 | −11.972 |

**不同**（差约 0.5，≈4.6%）。虽然 `loss` / `grad_norm` 只差 1e-5（决策几乎相同），
但 `r` 的差是真实的。**根因不是载量**：`ReferenceObjectives.of(inst, cfg)`（`f^ref`）
与参考运行**都随 `cfg.multi_drop` 变**——

| | `f^ref` | `w` | 参考 makespan |
|---|---|---|---|
| 带 `multi_drop` | (117.77, 8.81, **81.72**) | (0.0632, 0.8456, 0.0911) | 117.8 |
| 不带 | (117.31, 8.74, **161.17**) | (0.0660, 0.8859, 0.0481) | 117.3 |

即：它改的是**奖励归一化的参考点**（第三目标 TWT 的参考值差 2×），外加交付段的代码路径
（`_deliver_multi` 与单卸货点段是两处独立落点）。

**归因更正（2026-10-05）**：`SimConfig.multi_drop` 自己的 docstring（`des.py` 87–89 行）说的是
"打开后与旧配置读数不可比：makespan/能耗/趟数/行程都会变"——**从来没有断言 ⑩ 关时就惰性**。
"惰性"是**协调者由"容量恒 1"外推出来的推断，被本实测推翻**（不是代码注释说错）。
`_collect_multi` 的 docstring 那句"`capacity == 1` ⟹ 一件都不追加"**在采集段是对的**——
错的是把它外推到整条链。

**裁定：`multi_drop` 在被消融的 run 里仍照基线（= 开）。** 理由：

1. §9.3 已把它定为**"模型补完，不是加开关"**（`max_agv_capacity` 此前是死参数）⟹ 它是模型
   的一部分、不是 ⑩ 的机制（⑩ 的机制是拼批头 `batch_head`）。消融 run 只该改指定的那一项。
2. **更硬的一条**：`f^ref`/`w` 是**跨 run 共享的归一化基准**——只在 `c-none`/`c-no-logistics`
   两个 run 关掉它，这两个 run 的 `w` 就与其余 11 个 run**不可比**，消融表内部就不是同一把尺子。
   保持全开 ⟹ **13 个 run 共用同一个参考点**。
3. 物理上也一致：关 ⑩ 时开着 `multi_drop`，**交付模型仍是基线口径**。

受影响的 run 只有 `c-none` 与 `c-no-logistics`（它们把 ⑩ 关了）；其余 run ⑩ 都开、载量 > 1，
`multi_drop` 本就在起作用。

⚠️ 这条**要在论文里如实声明**：`multi_drop` 不是 ⑩ 的开关，它在 ⑩ 关时仍改参考点。
